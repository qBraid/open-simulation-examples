1 · the pitch, in one picture

Three horizons, one platform

Customers should be able to use the same environments, agents and compute from day one, whether or not they ever touch a QPU. Horizon 1 is what pays today. Horizons 2 and 3 are why the work is on qBraid and not a generic cloud.

Horizon 1 · value today

Open-source solvers, run by agents

OpenFOAM, FEniCSx, HiGHS, cuOpt, OpenMM, Palace, MuJoCo and others, packaged as qBraid environments. Agents set up the cases, run them on CPU and GPU instances billed by the hour, check the results against known answers, and render them in the browser with three.js.

$0 license · $0.24–$5.49/h compute
Horizon 2 · quantum today

Quantum as a benchmarked co-processor

The classical pipeline stays in charge. A small subproblem (a QUBO, an active space, a sampled distribution) goes to a QPU or GPU simulator through the same agent, and the answer is always scored against the classical baseline. The quantum-inspired methods are useful now. Real advantage is not claimed.

readiness experiments, not production
Horizon 3 · fault-tolerant future

Drop-in quantum kernels

Phase estimation for strongly correlated chemistry and materials is the most credible case. Quadratic speedups for Monte Carlo and search come after that, and only where overheads allow. A customer whose workflow already runs on qBraid swaps in a kernel. They don't rebuild the workflow.

3 · the thesis

Why agents change what open source can compete with

In most of these fields the solver is not what separates open source from commercial tools. The gap is everything around the solver: the GUI, meshing, case setup, validated defaults, support, and an engineer who knows the tool. Those are what agents are good at. The one field where the solver itself is the gap is hard mixed-integer optimization, and the page says so.

6 · how this lands in the skills architecture

Fits the existing layers, with one new cross-cutting skill

This plugs straight into the design record's four layers. Environments stay tool-specific (a cfd-stack, not an "aerospace env"), and sector skills stay thin routers. What's new is a family of simulation method skills that every sector shares. The one I'd build first is sim-viz, because it's where the wow comes from.

7 · recommended order

Build order: flagship demos first

Each wave follows the design record's process: run it for real on qBraid, write the skill from that run with a verification stamp, have a cold agent test it, then publish through the signed release path. Every verified run also doubles as a showcase for the Explore page.

Wave 1 · three flagships
  1. Virtual wind tunnel. cfd-stack (OpenFOAM + XLB), sim-viz, and V&V against the Re=100 cylinder and the lid-driven cavity.
  2. Fleet routing on a live map. optimization-stack (cuOpt, PyVRP, HiGHS) with solver-racing, then the same small instance run as QAOA. This lines up with the IBM webinar.
  3. Design a qubit, then run it. Palace + Qiskit Metal → Hamiltonian → CUDA-Q simulation → compared with real device calibrations. Nobody else can tell this story.
Wave 2 · breadth
  1. Virtual screening: Boltz batches on L4s, then OpenMM or OpenFE on the top hits, a 3D chemical-space cloud, and Mol* poses. This feeds the planned pharma router.
  2. Topology optimisation: FEniCSx, with the part evolving live in three.js.
  3. Robot policy: train with MuJoCo on a GPU, then run the policy in the browser with MuJoCo WASM + three.js.
Wave 3 · the rest of the map
  1. Energy (PyPSA scenario ensembles on a map), reusing optimization-stack.
  2. Weather (Earth2Studio + Aurora ensembles on a Cesium globe).
  3. Finance (QuantLib and Riskfolio with GPU Monte Carlo), plus materials (MLIP pre-screening → DFT).
8 · where I need you

Decisions for you

  • Wave 1: are these the right three? I'd keep "design a qubit" in, because it's the one only qBraid can do.
  • Environment size: one cfd-stack with OpenFOAM, SU2 and XLB together, or one environment per solver? Per solver is cleaner but gives the catalog more entries.
  • Where the pathway goes: this page is an internal draft. A public version needs marketing copy, the verified numbers, and a legal check on prices and licences.
  • Licence rules: skills recommend only OSI-licensed code and commercially usable weights. That excludes FluidX3D and the GraphCast weights, and the AGPL tools (OpenBB) get a warning.
  • Home disk is at 96% (2 GB free). Solver builds need to go on an on-demand instance or the overlay, not $HOME.
